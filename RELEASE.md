# Релизы и версии

Версия приложения берётся из последнего git-тега — вручную в `pyproject.toml`
её не задаём. Механика: `hatch-vcs` (setuptools_scm) при сборке читает теги и
формирует PEP 440-версию; сгенерированный `src/hsi_toolkit/_version.py`
(`__version__`) в git не коммитится.

## Схема версионирования (PEP 440)

| Тип               | Тег         | Версия сборки |
| ----------------- | ----------- | ------------- |
| Стабильный релиз  | `v0.2.0`    | `0.2.0`       |
| Release candidate | `v0.2.0rc1` | `0.2.0rc1`    |
| Beta              | `v0.2.0b1`  | `0.2.0b1`     |
| Alpha             | `v0.2.0a1`  | `0.2.0a1`     |

- Префикс `v` обязателен (условлен в release-воркфлоу и RELEASE-инструкции).
- Допустима форма с разделителем: `v0.2.0-rc.1` → нормализуется в `0.2.0rc1`.
- Пререлизы упорядочиваются до стабильной версии: `0.2.0rc1 < 0.2.0`.
- Коммиты после релиза (без тега) получают dev-версию вида `0.3.0.devN`
  (до первого тега — `0.0.1.devN`); вне git-репозитория (нет метаданных) —
  fallback `0.0.0`. Сборки без тега публиковать нельзя.

## Стабильный релиз

1. Убедиться, что `main` зелёный в CI (workflow **ci**).
2. Прогнать тесты локально: `uv run pytest -q`.
3. Поставить аннотированный тег на коммит в `main`:

   ```powershell
   git tag -a v0.2.0 -m "Release 0.2.0"
   git push origin v0.2.0
   ```

4. Workflow **release** на теге автоматически: гоняет тесты → собирает
   `dist\hsi-toolkit.exe` через PyInstaller → публикует exe артефактом и
   создаёт GitHub Release с автоматически сгенерированными notes.
5. Проверить страницу Releases; при необходимости отредактировать описание.

## Пререлиз

Аналогично, но тег с суффиксом пререлиза:

```powershell
git tag -a v0.2.0rc1 -m "Release candidate 0.2.0rc1"
git push origin v0.2.0rc1
```

Workflow определяет пререлиз по имени тега (`a`, `b`, `rc`, `dev` внутри тега)
и помечает GitHub Release флажком **Pre-release**. Артефакт `hsi-toolkit.exe`
прикладывается так же, как у стабильного релиза.

Теги — иммутабельная история: ошибочный пререлиз не переписываем, следующий
получает новый номер (`v0.2.0rc2`). Тег нужно удалить, только если он не
успел запушиться/собраться и ноль людей на него ссылается:

```powershell
git tag -d v0.2.0rc1
git push origin :refs/tags/v0.2.0rc1
```

## Локальная проверка версии

```powershell
uv sync --reinstall-package hsi-toolkit
uv run python -c "import hsi_toolkit; print(hsi_toolkit.__version__)"
uv build   # dist\hsi_toolkit-<версия>-py3-none-any.whl
```

Без тега — dev-версия (`0.0.1.devN`); на коммит после `v0.2.0` —
`0.3.0.devN`; после пуша тега и `uv sync --reinstall-package hsi-toolkit` —
точная версия тега (editable-установка кэшируется, поэтому нужен reinstall).

## Важные детали

- В `release.yml` checkout идёт с `fetch-depth: 0` — без полной истории теги
  не видны и соберётся fallback-версия. Не заменять на shallow checkout.
- Бэкенд сборки: `hatchling` + `hatch-vcs` (`[build-system]` и
  `[tool.hatch.*]` в `pyproject.toml`). Версия бэкендов фиксируется в
  `[build-system].requires` — поднимать её отдельным коммитом, не вместе с
  релизом.
- Изменение версии не требует обновления `uv.lock`: версия корневого проекта
  динамическая (`dynamic = ["version"]`).
